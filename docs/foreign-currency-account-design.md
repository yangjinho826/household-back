# 외화 계좌 설계 (Stage 5)

> 상태: **설계 검토용 초안 v2.** 구현 착수 전. 2026-08-17 작성, 같은 날 codex 교차검증 반영.
> 확정 = 계좌당 통화 1개 / KRW 를 합산 기준으로 유지 / 1차 범위는 **비투자 계좌만**.

## 1. 무엇을 하려는 건가

지금은 **모든 계좌가 원화**다. 실제로는 달러 예금 계좌를 쓰고 있고
(`토스뱅크 외화통장`), 그 잔액이 원화 숫자 하나로만 기록돼 있다.

Stage 4에서 한 건 **종목 단위 통화**다 — NASDAQ 종목을 `$230.38` 로 보여주는 것.
그런데 그 돈이 **어느 통화 지갑에서 나갔는지**는 여전히 원화로만 안다.

### 레퍼런스 — 토스는 어떻게 하나

| | 동작 |
|---|---|
| 토스뱅크 외화통장 | 한 계좌가 **17개 통화를 동시 보유**. 외화 상태로 보관하고 원할 때 환전 |
| 토스증권 | **달러 예수금**이 따로 있음. 원화로 주문하려면 환전하거나 오픈뱅킹으로 원화를 채움 |

핵심은 **잔액이 통화별로 따로 있고, 환전이 명시적 거래**라는 것.

출처: [토스뱅크 외화통장 총정리](https://www.tossbank.com/articles/money-management) ·
[토스증권 환전 수수료](https://support.toss.im/faq/3549)

## 2. 현재 구조 (실측)

### 계좌에 통화 개념이 없다

```python
# app/domain/account/model.py
class Account(BaseEntity):
    name / account_type / start_balance: Numeric(15,2) / color / icon / sort_order / is_archived
    # currency 없음
```

### 잔액 공식

```python
# app/domain/account/service.py:291 _cash_flow
start_balance + income - expense - transfer_out + transfer_in + valuation_net
```

계좌 타입별 분기 — 비투자는 위 현금 공식, 투자는 거기에 종목 평가액을 더한다:

```python
# 투자계좌 (service.py:333 부근)
cash    = 현금흐름 - pt_sums["buy"] + pt_sums["sell"]   # 매매 정산액은 KRW
balance = cash + portfolio_valuation                    # 종목 평가액도 KRW
```

### 이체는 있지만 환전은 담을 수 없다

```python
tx_type: TRANSFER
amount: Numeric(15,2)        # ← 금액이 하나뿐
to_account_id: UUID | None
```

`TRANSFER` 는 **출발 금액 = 도착 금액**을 전제한다. 환전은
`1,400,000원 출금 / $1,000 입금` 으로 **금액이 두 개**라 지금 모델로는 표현이 안 된다.

### 환율

`currency_rates` 는 pair 당 **1행(최신값)**뿐이다. 과거 환율 이력이 없다.

## 3. 핵심 설계 판단

### 3-1. KRW 를 합산 기준으로 유지한다 (초안에서 뒤집힘)

초안은 "계좌 현금은 재평가 수단이 환율뿐이니 **외화가 진실 원천**"이라고 썼다.
**이 방향을 버린다.** 투자계좌에서 다음이 성립하지 않기 때문이다:

```text
balance = cash + portfolio_valuation
        =  $1,000  +  ₩3,000,000        ← 단위가 다른 값을 더한다
```

종목은 Stage 4 에서 KRW 를 진실 원천으로 확정했는데 계좌만 외화로 뒤집으면
**같은 계좌 안에서 두 원칙이 충돌**한다. 그래서:

| 값 | 통화 | 성격 |
|---|---|---|
| `native_balance` | 계좌 통화 | 거래합 그대로. **원장의 진실** |
| `balance` | **KRW** | `native_balance × 현재환율`. 기존 필드 의미 그대로 유지 |

원화 계좌는 `native_balance == balance` 이고 환율은 1이라 **기존 동작이 그대로다.**
순자산·자산구성은 계속 `balance`(KRW)만 합산하므로 **합산 경로를 고치지 않아도 된다.**

> 초안이 걱정한 "환율이 올라도 자산이 안 늘어난다"는 문제는 여기서도 해결된다.
> `balance` 를 저장값이 아니라 **조회 시 현재 환율로 계산**하기 때문이다.

### 3-2. 1차 범위는 비투자 계좌만

외화 **투자**계좌는 이번에 하지 않는다. 그 경우 한 계좌 안에서

- 일반 입출금 `amount` → 계좌 통화(USD)
- 포트폴리오 매매 정산액 → KRW 박제값 (Stage 2·4 에서 확정)
- 종목 평가액 → KRW

세 가지가 섞여, `cash = cash - pt_sums["buy"] + pt_sums["sell"]` 가
**USD 현금에서 KRW 매수액을 빼는** 계산이 된다. 이걸 풀려면 매매 정산 통화까지
계좌 통화로 재정의해야 해서 Stage 4 를 다시 건드리게 된다.

실사용 대상(`토스뱅크 외화통장`)이 예금이므로 1차는 그걸로 충분하다.
**가드**: `account_type == INVESTMENT` 인 계좌는 `currency != 'KRW'` 를 거부한다.

### 3-3. 계좌 통화는 생성 후 불변

`transactions.amount` 의 통화를 계좌에서 도출하므로, `accounts.currency` 를 바꾸면
**과거 모든 거래 금액의 의미가 통째로 바뀐다.** 원화 계좌를 USD 로 바꾸는 순간
과거 `100000` 이 `₩100,000` 에서 `$100,000` 으로 재해석된다.

→ 수정 API 에서 `currency` 변경을 **거부**한다. 통화를 바꾸려면 계좌를 새로 만든다.

### 3-4. 필드 이름으로 통화를 드러낸다

`household.currency`(가계부 기준통화)가 이미 있고 여기에 `accounts.currency` 가
더해지면, 응답의 금액 필드가 어느 통화인지 이름만으로 구분되지 않는다.
`Money` 타입은 통화를 싣지 않는다.

규칙: **KRW 환산값은 기존 이름 그대로, 계좌 통화 원본은 `native_` 접두사.**
(Stage 4 의 `*_ccy` 는 "거래통화 원본"으로 이미 자리를 잡았으므로 재사용하지 않는다 —
`ccy` = 종목의 시장통화, `native` = 계좌통화로 갈라 둔다.)

## 4. 데이터 모델 변경

### 4-1. 계좌 통화 (Stage 5-1)

```sql
ALTER TABLE accounts ADD COLUMN currency CHAR(3) NOT NULL DEFAULT 'KRW';
```

- 계좌당 통화 **1개**. 달러 통장은 별도 계좌
- 기존 계좌는 전부 `KRW` → **기존 동작 완전 불변**
- 그 계좌의 거래 `amount` 는 **계좌 통화 기준**. 거래에 통화 컬럼을 두지 않는다
  (계좌에서 도출 — Stage 4 가 `Market.currency` 하나에서 도출한 것과 같은 사상)
- 응답에 `native_balance`(계좌 통화) + `balance`(KRW 환산) 병기

### 4-2. 환전 거래 (Stage 5-2)

```sql
ALTER TABLE transactions ADD COLUMN to_amount NUMERIC(15,2) NULL;
```

- `TRANSFER` 에서만 사용. **NULL 이면 기존 동작**(출발=도착 금액)
- 통화가 다른 두 계좌 간 이체 = 환전. `amount`(출발 통화) / `to_amount`(도착 통화)
- 적용 환율은 두 값의 비율로 나온다

**한계**: 이 구조는 금액 이동만 표현한다. 환전 **수수료·우대율·기준환율·환전손익**은
별도 개념으로 남지 않는다. "환전으로 이익을 봤는가"를 물으면 두 값의 비율밖에 없고,
그 비율이 실제 체결조건인지 입력 실수인지 검증할 근거가 없다.
1차에서는 감수하고, 필요해지면 수수료를 별도 지출 거래로 분리하는 쪽을 검토한다.

## 5. 영향 범위

`balance` 를 KRW 로 유지하기로 했으므로 **합산 경로는 손대지 않는다.**

| 위치 | 조치 |
|---|---|
| `wealth/service.py:54` 순자산 합산 | **변경 없음** — 계속 `balance`(KRW) 합산 |
| `account/service.py:291 _cash_flow` | **변경 없음** — 한 계좌 안은 단일 통화 |
| `_calc_cash_balance` | `native_balance` 산출 후 **환율을 곱해 `balance`** 생성 |
| `AccountResponse` | `native_balance` / `currency` 추가 |
| 계좌 생성·수정 | 투자계좌 외화 거부(§3-2), 통화 변경 거부(§3-3) |
| 프론트 | 외화 계좌만 `$1,000` 주 + `₩1,4xx,xxx` 보조 |

### 검증해야 할 불변식

- `순자산 = Σ(계좌 balance) + Σ(종목 평가액)` — 기존과 동일한 식이 유지되는가
- 원화 계좌만 있는 가계부의 모든 숫자가 **도입 전과 완전히 동일**한가 (회귀)
- 환율이 바뀌면 **거래 없이도** 순자산이 변한다 → 아래 §6-2

## 6. 미해결로 남기는 것

### 6-1. 스냅샷 — 셋 중 하나는 포기해야 한다

박제 값으로 무엇을 남기든 하나는 깨진다:

- 과거 시점의 **원본 외화 잔액** 복원
- 과거 시점의 **KRW 순자산** 재현
- 환율 **정정·재계산** 가능성

**채택**: `account_snapshots` 에 `native_balance` 와 `balance`(그 시점 환율로 환산한 KRW)를
**둘 다** 박제한다. 그러면 앞의 둘은 살고 세 번째(환율 정정)만 포기한다.
과거 환율 이력 테이블 없이 가능한 최선이다.

> 관련 선재 결함: `market_price/service.py:171` 의 `backfill_yahoo_monthly` 가
> 과거 월봉을 **현재 환율**로 KRW 환산한다(주석에 "근사"로 이미 기록됨).
> 같은 뿌리의 문제라 환율 이력을 도입하면 함께 해소된다.

### 6-2. 환차손익의 자리가 없다

외화 잔액을 현재 환율로 평가하면 **거래 없이 순자산이 변한다.** 이 변화분은
거래도 아니고 `VALUATION`(평가조정)도 아니라서 어디에도 명시적으로 잡히지 않는다.

그래서 "이번 달 자산이 왜 늘었는가"를 물으면 **현금 환차익 / 종목 가격 변동 /
종목 환율 효과**를 분리할 수 없다.

더 근본적으로, 코드 안에 성격이 다른 두 방식이 공존하게 된다:

| 방식 | 예 |
|---|---|
| 평가변동을 **거래로 누적** | `VALUATION` — 수동자산(부동산·연금·금) |
| 평가변동을 **현재 시세로 즉시 파생** | 종목(`current_price`), 외화 현금(환율) |

둘 다 같은 `balance` 로 흘러가고 스냅샷·월별 흐름에서 구분되지 않는다.
1차 범위에서는 **분해하지 않고 기록만** 한다. 필요해지면 월별 리포트에
"환율 효과" 항목을 분리하는 것이 후속 과제다.

## 8. 단계 분할

| 단계 | 내용 | 마이그레이션 |
|---|---|---|
| **5-1** | `accounts.currency` + `native_balance` + 이중 표시 + 가드 2개 | 1 (additive) |
| **5-2** | `transactions.to_amount` + 환전 거래 UI | 1 (additive) |

수입/지출로 가능하고, 원화↔달러 이동은 5-2 가 있어야 정확해진다.
