# 다중 인스턴스 멱등성 실증 (2026-08-03)

> 로드맵 마지막 항목(`docs/portfolio-sre-roadmap.md` "실증" 행)의 산출물.
> 결론 한 줄 — **상태를 DB 에 둔 것만 인스턴스 안전하다.** 멱등성·advisory lock 은 프로세스
> 경계를 넘어도 성립했고, 프로세스 메모리에 둔 알림 쿨다운은 인스턴스마다 따로 셌다.

---

## 1. 무엇이 미증명이었나

기존 테스트는 동시성을 검증했지만 전부 **한 프로세스 안**이었다.

| 기존 검증 | 실제 범위 | 미증명 구간 |
|---|---|---|
| A11 멱등성 동시 N발 | `httpx.ASGITransport` — 한 프로세스·한 이벤트 루프 | 프로세스 경계·독립 커넥션 풀·실 HTTP 스택 |
| B6 잡 동시 진입 | 한 프로세스 안 세션 2개 (`pg_backend_pid()` 상이는 단언) | `scheduler.py` docstring 의 "다중 인스턴스/워커" |
| 알림 쿨다운 한계 | `alert.py` 주석에 **서술만** | 실측 없음 |
| 2컨테이너 동시 기동 | — | `entrypoint.sh` 의 `alembic upgrade head` 경합 |

가설: 멱등성(`ON CONFLICT` 상태머신)·advisory lock 은 판정 상태가 **DB** 에 있으니 안전해야 하고,
알림 쿨다운은 **프로세스 메모리 dict** 에 있으니 안 되어야 한다. 이 대비를 실측으로 확인한다.

---

## 2. 실증 구성 — 2층

같은 명제를 층위를 달리해 두 번 확인한다. 층마다 증명하는 게 다르다.

| 층 | 구성 | 무엇을 보장 | 산출물 |
|---|---|---|---|
| **회귀 게이트** | 호스트에 uvicorn 프로세스 2개 (`tests/multi_instance/`) | 매 PR·배포마다 재검증 (`test.yml` reusable 이라 자동 편입) | 테스트 6개 |
| **운영 구성 재현** | Docker 이미지 2개 (`docker-compose.multi.yml`, entrypoint→alembic→uvicorn) | 운영과 같은 이미지·기동 경로·컨테이너 경계 | 1회 실증 로그 |

**LB 를 두지 않는다.** 앞단에 라운드로빈을 두면 두 요청이 같은 인스턴스로 갈 수 있어 "서로 다른
프로세스가 경합했다"를 보장하지 못한다. 클라이언트가 포트(8101/8102) 또는 서비스명(app1/app2)을
직접 지정하고, 각 주소는 서로 다른 PID/컨테이너가 단독으로 바인딩한다 → **주소 지정 = 인스턴스 지정**.

재현:

```bash
# 회귀 게이트
docker compose -f docker-compose.test.yml up -d
uv run pytest tests/multi_instance -q

# 운영 구성 재현
docker compose -f docker-compose.multi.yml up -d --build
docker compose -f docker-compose.multi.yml run --rm --no-deps --entrypoint "" \
    app1 /app/.venv/bin/python -m tests.multi_instance.proof_run
```

## 3. 결과

### 3-1. 회귀 게이트 (pytest 6개, 전체 59 → **65 passed**)

| # | 시나리오 | 결과 |
|---|---|---|
| E0 | 두 인스턴스가 서로 다른 프로세스인가 (PID 상이 + 각자 응답) | ✅ 이하 전부의 전제 |
| E1 | 동일 키를 인스턴스 A·B 에 동시 투입 | ✅ 거래 **1건**, 멱등 레코드 1건, 응답 ⊆ {200, 409} |
| E1-nc | 같은 하니스에서 키 헤더만 제거 (negative control) | ✅ 거래 **2건** — E1 의 1건이 순차 우연이 아님을 역증명 |
| E2 | 10발을 A·B 에 5:5 분배 | ✅ 거래 **1건** |
| E3 | 프로세스 2개가 같은 잡 이름으로 동시 진입 | ✅ 정확히 **1개만 RAN**, 나머지 SKIPPED, 행 1건 |
| E4 | 두 프로세스에서 같은 key 알림 쿨다운 판정 | ✅ **둘 다 first=True** — 쿨다운은 인스턴스별 |

라우팅 증거 (실제 로그, 같은 user·같은 초):

```
instance-8101 | app.access                    | POST /transaction/create 200 user=9b926d4b-... ip=127.0.0.1 42ms
instance-8102 | app.core.idempotency.service  | idempotency cache hit: key=e1-22ffc774 user=9b926d4b-...
```

한 요청은 8101 이 원본으로 처리하고, 같은 키의 다른 요청은 **8102 가 자기 프로세스에서 캐시로 재생**했다.

3회 모두 최종 판정 PASS. `거래 행(즉시)` 가 흔들리는 것은 §4-3 발견으로 이어진다.

### 3-3. 두 컨테이너 동시 기동 (S3)

```
app1-1 | INFO [alembic.runtime.migration] Context impl PostgresqlImpl.     09:51:26
app2-1 | INFO [alembic.runtime.migration] Context impl PostgresqlImpl.     09:51:26
```

같은 초에 두 컨테이너가 각자 `alembic upgrade head` 를 실행했고 둘 다 정상 기동했다.
**단, 이때 적용할 리비전이 없는(no-op) 상태였다** — 미적용 리비전이 있는 상태의 동시 기동은
검증하지 않았다(§5 한계).

두 인스턴스 모두 자기 APScheduler 에 잡 5개씩 등록한 것도 함께 확인했다 — 같은 cron 이 양쪽에서
발사되는 구성이며, 그래서 E3(advisory lock)이 실제로 필요한 방어다.

## 4. 발견 3건

### 4-1. `ddl/init.sql` 이 baseline 에서 드리프트해 새 환경을 스키마부터 만들 수 없다 🔴

실증 스택을 빈 볼륨으로 띄우다 앱 컨테이너 2개가 동시에 죽었다.

```
sqlalchemy.exc.ProgrammingError: column "amount" of relation "fixed_expenses" does not exist
[SQL: ALTER TABLE fixed_expenses DROP COLUMN amount]
```

- `ddl/init.sql` 은 alembic baseline(`be504a39cec0`, 빈 마이그레이션) 시점의 스냅샷이어야 한다.
- 그런데 init.sql 의 `fixed_expenses` 에는 이미 `amount` 가 없고, 리비전 `a9668f7687a9` 는 그 컬럼을 `DROP` 하려 한다 → 체인이 끊긴다.
- **운영은 이 경로를 타지 않는다** — 이미 `stamp head` 상태라 증분만 적용해 왔다. 재해복구도 `pg_dump` 스냅샷 복원이라 무관하다.
- 영향 범위 = **새 환경을 스키마부터 구축하는 경로**(신규 개발자 로컬 / 스테이징 / 완전 재구축).
- 이번 실증에서는 `tests/multi_instance/init_proof_schema.py`(런타임 모델로 `create_all` + `stamp head`)로 우회했다. 결과 스키마는 운영과 동등하고, 앱 컨테이너는 entrypoint 의 alembic 을 그대로 타서 기동 경로는 유지된다.
- **근본 수정은 이 실증의 범위 밖**이다(init.sql 을 baseline 시점으로 되돌리거나, baseline 을 현재 스키마로 재작성하는 선택지가 갈린다). `migration-playbook.md` 의 후속 항목으로 남긴다.

### 4-2. 멱등 캐시로 재생된 요청은 access log 에 남지 않는다 🟡

`main.py` 의 `add_middleware` 순서상 마지막에 추가된 `IdempotencyMiddleware` 가 가장 바깥이고
`AccessLogMiddleware` 가 안쪽이다. 캐시 히트는 바깥에서 바로 반환되므로 access log 를 타지 않는다.

- 실증 중 라우팅 증거를 access log 로 잡으려다 8102 쪽에서 기록이 없어 발견했다(§3-1 로그 참조 — 8102 는 서비스 로그에만 남았다).
- 관측 영향: **멱등 재시도 트래픽이 access log 에서 보이지 않는다.** 재시도가 얼마나 오는지, 어떤 클라이언트가 중복 전송하는지 access log 로는 알 수 없다.
- 미들웨어 순서를 바꾸면 해결되지만 그건 멱등 판정보다 로깅을 먼저 태우는 설계 변경이라, 실증 범위에서는 **기록만 하고 소스는 건드리지 않는다.**

### 4-3. HTTP 200 수신이 DB 커밋 가시성을 보장하지 않는다 🟡

M1-nc(멱등 보호 없음)에서 응답 2건을 모두 받은 **직후** 집계가 3회 실행에서 각각 1 / 0 / 0 이었고,
잠시 뒤 최종값은 항상 2였다. 반면 M1(멱등키 있음)은 즉시값도 3회 모두 1로 안정적이었다.

| 경로 | 즉시 집계 | 최종 집계 |
|---|---|---|
| 멱등키 있음 | 1 / 1 / 1 (안정) | 1 |
| 멱등키 없음 | 1 / 0 / 0 (흔들림) | 2 |

- 유력한 설명: 멱등 경로는 미들웨어가 응답 body 를 끝까지 읽은 뒤 자기 세션을 커밋하고 반환하므로 응답 시점에 라우터 커밋도 끝나 있다. 보호가 없으면 그 동기화 지점이 없어 `BaseHTTPMiddleware` 스트리밍 구조에서 응답 송신과 의존성 teardown(=`get_db` 커밋)이 겹칠 수 있다. **메커니즘은 가설, 흔들림 자체는 실측이다.**
- 검증 방식에 반영: 순간값이 아니라 **최종 상태**를 단언하도록 `_settled_count`(기대값 도달까지 폴링 + 도달 후 settle 재확인)를 도입했다. settle 재확인은 반대 방향 오판(늦게 한 건 더 들어오는데 먼저 통과)도 막는다.
- 운영 함의: "200 받았으니 DB 에 있다"를 전제로 한 클라이언트 후속 동작(즉시 재조회)은 아주 짧은 창에서 빗나갈 수 있다. 실사용 규모에서 관측된 적은 없다.

## 5. 감수한 한계 (면접 재료)

- **인스턴스 2개까지만.** N 을 늘렸을 때의 경합 특성(락 대기, 커넥션 수)은 미검증.
- **동일 호스트.** 네트워크 분단·시계 오차 같은 진짜 분산 환경 변수는 없다.
- **alembic 동시 기동은 no-op 상태에서만 관측.** 미적용 리비전이 있는 상태의 동시 기동은 미검증이며, 그 경우의 절차는 `migration-playbook.md` 소관.
- **E3 의 증명력 한계.** advisory lock 은 판정 단위가 **커넥션**이라, 프로세스를 나눈다고 락 의미론이 달라지지 않는다. E3 가 새로 보장하는 건 락 의미론이 아니라 **배선** — 각자 스케줄러를 띄운 두 프로세스가 실제로 1개만 통과한다는 것.
- **§4-3 의 메커니즘은 가설.** 흔들림은 재현했지만 원인을 코드 레벨로 못박지는 않았다.
- **§4-1 은 우회했을 뿐 안 고쳤다.** 새 환경 구축 경로는 여전히 깨져 있다.

## 6. 경계 — 인스턴스 안전한 것과 아닌 것

| 대상 | 상태 위치 | 다중 인스턴스 | 근거 |
|---|---|---|---|
| POST 멱등성 | DB (`idempotency_records`, `ON CONFLICT`) | ✅ 안전 | E1 / E2 / M1 |
| 스케줄 잡 중복 방지 | DB (`pg_try_advisory_xact_lock`) | ✅ 안전 | E3 |
| 알림 쿨다운 | **프로세스 메모리** (`_last_sent_at` dict) | ❌ 인스턴스별 | E4 |
| 멱등 재시도 관측 | — | ⚠️ access log 사각 | §4-2 |

알림 쿨다운을 다중 인스턴스로 가져가려면 판정 상태를 공유 저장소로 옮겨야 한다(같은 DB 에 얹으면
인프라 추가 0 을 유지할 수 있다). 지금은 단일 인스턴스 운영이라 옮기지 않았다 — **"안 되는 걸 몰라서"가
아니라 "안 해도 되는 규모라서"** 이고, 그 경계를 숫자로 확인해 둔 게 이 실증의 결론이다.
